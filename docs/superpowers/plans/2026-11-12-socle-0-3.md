# Socle 0.3 : le cœur de l'API

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for
> tracking.

**Goal :** donner à `popote-api` tout ce que chaque route des étapes suivantes réutilisera : journal et traces,
limites, garde d'origine, base à deux contextes (personne, service), nouvelle porte du service, lecture de la
session et `GET /api/v1/me`, idempotence, requêtes conditionnelles, contrat OpenAPI gardé par la CI, routes
internes signées ; et appliquer les migrations sur l'essai par la CI. Rien ne change pour Kamil.

**Architecture :** référence unique : `popote-web/docs/superpowers/specs/2026-11-12-socle-design.md` (« la
spec »), surtout § 2, § 3, § 4 (lecture de session seulement), § 5.1, § 5.3, § 7, § 8.2, § 9. Les fiches
`popote-api/docs/normes-api.md`, `securite.md`, `exploitation.md` en sont extraites et sont mises à jour par
chaque tâche qui change ce qu'elles décrivent. Le squelette de 0.2 est la base : `errors.py` (Problem Details,
règle « une route lève `Probleme`, un middleware rend `reponse(...)` »), `identifiant.py`, `relais.py` (garde de
l'en-tête secret, `ip_de`), `infra/db.py` (sonde), `config.py`.

**Tech Stack :** Python 3.13, uv 0.10.7 (`exclude-newer` du `pyproject.toml` : rien de publié depuis moins de
deux semaines), FastAPI, Pydantic v2, psycopg 3 + `psycopg_pool`, pytest, ruff, mypy strict ; Supabase CLI
(pile locale) ; GitHub Actions ; `oasdiff` ; Schemathesis.

**Hors périmètre :** la connexion elle-même (mots de passe, création et rotation de session, appareils,
invitations, réinitialisation, journal de sécurité : 0.4), les routes des domaines (0.5), l'IA (0.6), la
fermeture de la base (0.7), le client généré du front (avec son premier usage, 0.4 ou 0.5), l'export
OpenTelemetry et le suivi des erreurs hébergé (avec la décision D4 de Kamil : ici une prise sans effet).

- **Base locale partagée** (`npx supabase start`, port 54322) : seules les tâches de la voie « base » (T4 à T7,

- **Prod** : interdite. Aucune migration, aucune écriture, aucune lecture depuis ces tâches.
- **Secrets** : seulement `~/.config/popote/secrets.env`, lus sans jamais afficher une valeur.
- **Fini** = tests verts en local (`uv run pytest`, et `npx vitest run` si la base change), CI verte, revue

- **Journal** : aucune donnée personnelle (ni e-mail, ni prénom, ni montant, ni adresse IP, ni chemin brut
  qui pourrait porter un jeton) ; un message d'erreur de la base n'est jamais journalisé tel quel (son
  `DETAIL` recopie des valeurs) : seulement `sqlstate`, contrainte, table.

### T2 : Le journal en JSON et le contexte de trace W3C

**Pourquoi :** spec § 3.11 et § 10. Les journaux de Scaleway se lisent ligne par ligne : une ligne = un objet
JSON, avec l'identifiant de requête et de trace.

**Fichiers :** `src/popote_api/journal.py`, `src/popote_api/trace.py`, `src/popote_api/suivi.py`,
`src/popote_api/main.py`, `src/popote_api/errors.py` (appel de la prise de suivi), `Dockerfile`
(`--no-access-log`), tests `tests/unit/test_journal.py`, `tests/unit/test_trace.py`.

- [ ] `trace.py` : middleware ASGI pur. Lit `traceparent` (W3C Trace Context niveau 1, § 3.2) : version
  `00`, `trace-id` 32 hex minuscules non nul, `parent-id` 16 hex non nul, drapeaux 2 hex ; toute forme invalide
  (majuscules, longueur, tout zéro, version `ff`) est ignorée et une nouvelle trace commence. Crée un
  `span-id` propre à la requête. Pose `trace_id` et `span_id` dans des `ContextVar` et dans `scope["state"]`.
  `tracestate` n'est pas interprété. Pas de SDK OpenTelemetry à cette étape (temps de démarrage à froid,
  aucun récepteur choisi) : le format est celui d'OpenTelemetry, l'export viendra avec D4.
- [ ] `journal.py` : un formateur JSON (`ts` RFC 3339 UTC, `level`, `logger`, `msg`, `request_id`,
  `trace_id`, `span_id`, et les champs `extra` autorisés par une liste fermée) ; `configure()` remplace la
  configuration d'uvicorn (`uvicorn`, `uvicorn.error`) et la racine ; idempotente ; désactivable pour les
  tests par un réglage. Une exception se journalise avec sa pile, mais pour `psycopg.Error` seulement
  `sqlstate`, `constraint_name`, `table_name` (jamais `str(exc)`).
- [ ] Journal d'accès maison (uvicorn lancé avec `--no-access-log`) : une ligne par réponse, `method`,
  `route` = **gabarit** de la route (`scope["route"].path_format`, ou `"(aucune)"` si rien ne correspond),
  jamais le chemin brut ni la chaîne de requête ; `status`, `duration_ms`. Ni IP, ni agent utilisateur.
- [ ] `suivi.py` : `signale(exc, request_id)`, sans effet tant que D4 n'est pas tranchée ; appelée par le
  gestionnaire des 500.
- [ ] Tests : `traceparent` valide repris (même `trace-id`, nouveau `span-id`) ; chaque forme invalide
  ignorée ; ligne d'accès contient le gabarit `/api/x/{id}` et pas la valeur ; une 500 produit une seule
  ligne d'erreur avec `request_id` et `trace_id` ; une erreur psycopg journalisée sans son message.

### T3 : Les limites et la garde d'origine

**Pourquoi :** spec § 3.6, § 3.10, § 4 (CSRF), § 7.1 (API4, API8).

**Fichiers :** `src/popote_api/security/__init__.py`, `security/debit.py`, `security/origine.py`,
`src/popote_api/limites.py` (taille, type, délai), `config.py`, `main.py`, tests unitaires associés,
`docs/normes-api.md` (en-têtes exacts, brouillon cité par son numéro).

- [ ] **Taille** (middleware ASGI pur, rend `reponse(...)`) : `413` si `Content-Length` > 1 Mio, et aussi si
  le corps reçu en flux dépasse 1 Mio sans `Content-Length` (compter les octets de `receive`).
- [ ] **Type** : sur `POST`, `PUT`, `PATCH` avec un corps, `415` si le type n'est pas `application/json`
  (paramètre `charset` toléré) ; `PATCH` accepte aussi `application/merge-patch+json` (RFC 7396). Une liste
  d'exceptions par préfixe est prévue pour les photos (§ 6.1), vide ici.
- [ ] **Délai** : 30 s par requête ; au-delà `503`, code `delai_depasse`, `Retry-After`. Vérifier qu'une
  requête annulée pendant une transaction rend sa connexion propre au pool (à éprouver de nouveau en T4).
- [ ] **Débit** (dépendance FastAPI, pas middleware) : en mémoire par instance, fenêtre glissante ou seau à
  jetons ; lecture (`GET`, `HEAD`) 120/min, écriture 30/min ; clé = empreinte de la session quand T6 existe,
  sinon `ip_de(request)`, sinon une clé commune « sans-ip ». Nombre de clés borné (les plus anciennes
  oubliées) : un afflux d'adresses ne fait pas grossir la mémoire sans fin. En-têtes `RateLimit-Policy` et
  `RateLimit` selon la **dernière version** du brouillon IETF `draft-ietf-httpapi-ratelimit-headers` (la
  vérifier, citer son numéro) ; `429` + `Retry-After` en secondes entières. `/api/healthz` et `/api/readyz`
  ne sont pas limités.
- [ ] **Origine** (dépendance sur les méthodes qui écrivent) : `Origin` doit appartenir à
  `settings.origines` (prod : `https://notre-popote.fr` ; essai : `https://essai.notre-popote.fr` et le motif
  des aperçus Cloudflare, écrit dans la config ; local : `http://localhost:5173`, `http://127.0.0.1:5173`) ;
  `Sec-Fetch-Site`, s'il est présent, vaut `same-origin` ; l'en-tête propre à l'appli `X-Popote-Client: web`
  est exigé. Sinon `403`, code `origine_refusee`. `/internal/*` exempté (T10, signature).
- [ ] Tests : 1 Mio passe, 1 Mio + 1 octet `413` (avec et sans `Content-Length`) ; `text/plain` `415` ; un
  gestionnaire lent `503` avec `Retry-After` ; 121e lecture et 31e écriture en `429`, en-têtes présents et
  cohérents, fenêtre qui se libère avec une horloge factice ; clés bornées ; origine absente, étrangère, ou
  `Sec-Fetch-Site: cross-site`, ou sans `X-Popote-Client` : `403` ; origine juste : passe.

### T4 : La base : deux pools, deux contextes, les erreurs de la base

**Pourquoi :** spec § 5.1 (« qui exécute quoi »), § 8.2 (« transactions explicites, ouvertes dans le bon
contexte ; une erreur de la base devient un Problem Details »).

**Fichiers :** `src/popote_api/infra/db.py`, `config.py` (`database_url` = rôle `popote_api`,
`database_url_internal` = rôle `popote_internal`, tous deux exigés hors local), `main.py` (cycle de vie :
pools ouverts sans attendre de connexion, fermés à l'arrêt), `errors.py` (correspondance des erreurs psycopg),
`pyproject.toml` (`psycopg-pool`), `supabase/config.toml` (pooler local en mode transaction, si la pile locale
l'accepte pour des rôles à nous), `.github/workflows/ci.yml` (ne plus exclure `supavisor` si le pooler local
sert aux tests), tests `tests/integration/test_contextes.py`.

- [ ] Deux `AsyncConnectionPool` (`prepare_threshold=None`, petite taille, `min_size=0` : le conteneur dort
  à zéro instance), délai d'attente d'une connexion borné → `503 base_indisponible`.
- [ ] `async with base.personne(personne_id)` : transaction ; `set local role authenticated` ;
  `select set_config('request.jwt.claims', <json {"sub": id, "role": "authenticated"}>, true)` ; rend un
  curseur ; `commit` en sortie normale, `rollback` sur exception.
- [ ] `async with base.service()` : pool `popote_internal` seulement ; `set local role service_role` ;
  revendication `{"role": "service_role"}`. Seul le code de T10 (et plus tard l'invitation, les purges)
  l'appelle : une règle de Semgrep ou un test d'architecture interdit son import ailleurs.
- [ ] La sonde de `/api/readyz` passe par le pool `popote_api`.
- [ ] Erreurs : `23505` → `409 conflit` ; `23503`, `23514`, `22P02` → `422 donnees_invalides` sans pointeur ;
  `42501` (droit refusé, RLS) → `404 introuvable` (on ne révèle rien) ; `40001`, `40P01` → `503` avec
  `Retry-After: 1` ; `57014` → `503 delai_depasse` ; erreur de connexion → `503 base_indisponible`. Journal :
  `sqlstate`, contrainte, table, jamais le message. Les codes métier propres à une fonction SQL arriveront avec
  leur domaine (0.5).
- [ ] Tests d'intégration (base locale ; par le pooler en mode transaction si la pile locale le permet pour
  `popote_api` et `popote_internal`, sinon en direct, et l'écart est écrit ; les DSN distants de
  `test_roles.py` permettent de rejouer sur l'essai) : dans `personne(p)`, `auth.uid() = p` et
  `current_user = authenticated` ; à la connexion suivante tirée du même pool, `current_user = popote_api` et
  revendication vide ; une exception dans le contexte annule et rend une connexion propre ; la RLS ne montre
  que le foyer de `p` (deux foyers semés par le test) ; dans `service()`, `current_user = service_role` ;
  pool épuisé → `503`. **Le test « le pool personne qui pose la revendication `service_role` échoue sur
  `rappels_a_envoyer` »** arrive avec T5, avant ce code.

**Pourquoi :** spec § 5.1, « la porte du service ne se fie plus à une revendication ». Migration **compatible**
avec l'appli en ligne (ses fonctions Edge passent par PostgREST, donc `session_user = 'authenticator'`).

**Fichiers :** `supabase/migrations/0131_porte_du_service.sql`, `tests/integration/test_porte_du_service.py`,
`docs/securite.md`.

- [ ] Inventaire d'abord (dans la description de la PR) : chaque appelant de `is_service_role()` (fonctions,
  déclencheurs) et chaque fonction réservée au service (`rappels_a_envoyer`, `reserve_rappel`, … : celles qui
  refusent si ce n'est pas le service), avec qui l'appelle aujourd'hui (fonction Edge, `pg_cron`, front). Si
  une tâche `pg_cron` ou un script appelle l'une d'elles directement en `postgres`, le dire : le nouveau test
  ne l'accepterait plus (aujourd'hui non plus, sauf revendication posée : à vérifier).
- [ ] `is_service_role()` réécrite : `session_user = 'popote_internal'` **ou** (`session_user = 'authenticator'`
  **et** revendication `role = service_role`) ; `set search_path = ''` ; commentaire SQL qui date la seconde
  branche (retirée à J+2, § 11). Même signature, même volatilité.
- [ ] `revoke execute` de ces fonctions réservées à `public`, `anon`, `authenticated` ; `grant` à
  `service_role` (et `popote_internal` si nécessaire). Le retour arrière est écrit en commentaire en tête.
- [ ] Tests (psycopg, base locale ; `set session authorization` en super-utilisateur pour simuler
  `authenticator`) : `authenticator` + revendication service → vrai ; `authenticator` sans revendication →
  faux ; `popote_api` + `set local role authenticated` + revendication `service_role` posée par `set_config` →

  fonction `security definer` appelée par `popote_api`, toujours faux ; `authenticated` n'a plus `execute`
  sur les fonctions réservées (`42501`).
- [ ] La suite `npx vitest run` (tests de base repris, fonctions Edge comprises) reste verte : c'est la preuve
  que l'appli actuelle n'est pas cassée.
- [ ] Revue adverse **en base** (`pg_get_functiondef`, droits par `has_function_privilege`), et mutation :

### T6 : Lire la session, et `GET /api/v1/me`

**Pourquoi :** spec § 3.10 (toute route exige une session), § 4 (la session vit en base, le cookie n'en porte
que l'identifiant), et le livrable `/api/v1/me` de 0.3. La **création** d'une session (connexion) est 0.4 : ici
les tests la posent directement en base.

**Fichiers :** `supabase/migrations/0132_session.sql`, `src/popote_api/security/session.py`,
`src/popote_api/api/moi.py`, `src/popote_api/schemas/moi.py`, `config.py` (nom et attributs du cookie :
`__Host-popote_session` hors local, configurable en local), `main.py` (routeur `/api/v1`), retrait des routes
de preuve (`api/preuves.py`, son test, son montage), tests `tests/integration/test_moi.py`,
`tests/integration/_sessions.py` (fabrique de personnes et de sessions de test).

- [ ] Table `session` (nom de la spec ; le citer entre guillemets si le mot gêne) : `id` uuid, `token_hash`
  bytea unique (SHA-256 du jeton de 256 bits), `person_id` → `auth.users` (suppression en cascade),
  `created_at`, `last_seen_at`, `expires_at` (30 jours glissants), `absolute_expires_at` (90 jours),
  `revoked_at`. RLS activée, aucune politique pour `anon` ni `authenticated`, tous droits retirés.
- [ ] Fonction `security definer`, `search_path = ''`, exécutable par `popote_api` seulement :
  `session_personne(p_hash bytea) returns uuid` — la personne si la session n'est ni révoquée, ni échue, ni au
  bout de ses 90 jours ; repousse l'échéance glissante et `last_seen_at` au plus une fois toutes les 5 minutes
  (§ 3.6) ; `null` sinon.
- [ ] Dépendance `personne_connectee` : cookie absent, mal formé (pas 32 octets en base64url), inconnu, échu
  ou révoqué → `401 pas_de_session` avec un `WWW-Authenticate` (RFC 9110 § 15.5.2 l'exige ; schéma choisi et
  écrit dans `normes-api.md`) ; une comparaison par empreinte, jamais le jeton en clair en base ni au journal.
  La clé de débit de T3 devient l'empreinte de la session.
- [ ] `GET /api/v1/me` (contexte personne) : `{"id", "email", "display_name", "household": {"id", "name"} |
  null}` (vérifier les tables `user_profile` et `household`, `docs/schema.md`) ; `Cache-Control: no-store` ;
  `ETag` fort tiré du contenu et `304` sur `If-None-Match` égal (outil de T8 s'il est fusionné, sinon le
  poser ici et T8 le reprend).
- [ ] Tests : sans cookie, cookie mal formé, inconnu, échu, révoqué, au bout des 90 jours → `401` en
  `problem+json` avec `WWW-Authenticate` ; valide → `200` avec sa propre personne et son foyer ; deux
  personnes de deux foyers ne voient que le leur ; `If-None-Match` égal → `304` sans corps ; la fonction n'est
  pas exécutable par `authenticated` ni `anon` ; `last_seen_at` n'est pas réécrit à chaque requête.

### T7 : L'idempotence des `POST`

**Pourquoi :** spec § 3.5. Brouillon IETF `draft-ietf-httpapi-idempotency-key-header` (la spec dit version 08 :
vérifier la dernière et citer son numéro).

**Fichiers :** `supabase/migrations/0133_idempotence.sql`, `src/popote_api/security/idempotence.py`, tests
`tests/integration/test_idempotence.py` (avec une route de test montée par le test seulement, dont l'effet est
une ligne dans une table de test créée par le test).

- [ ] Table `idempotency_key` : `person_id`, `key` (1 à 255 caractères ASCII imprimables), `method`, `path`,
  `fingerprint` (SHA-256 de méthode, chemin et corps), `status`, `headers` (liste fermée), `body`,
  `created_at`, `expires_at` (+ 24 h) ; clé primaire (`person_id`, `key`) ; RLS `person_id = (select
  auth.uid())` pour `authenticated` ; purge des lignes échues (fonction SQL + tâche `pg_cron` quotidienne,
  écrite dans la migration, ou route interne de T10 : choisir et écrire pourquoi).
- [ ] Mécanique, **dans la même transaction que l'effet** (contexte personne) : `pg_try_advisory_xact_lock`
  sur (personne, clé) → refusé : `409 requete_en_cours` ; ligne existante et non échue : même empreinte →
  rejouer statut, en-têtes et corps ; autre empreinte → `422 cle_idempotence_reutilisee` ; sinon exécuter
  l'effet puis écrire la ligne. Une exception annule tout : rien n'est gardé, un nouvel envoi refera l'effet.
  En-tête absent → `400 cle_idempotence_manquante` ; mal formé → `400`. La forme de l'en-tête suit le
  brouillon (chaîne de champ structuré, RFC 9651).
- [ ] Un décorateur ou une classe de route que les `POST` des étapes suivantes poseront en une ligne.
- [ ] Tests : sans en-tête `400` ; premier envoi `201` et effet fait ; même clé même corps → même réponse,
  effet non refait ; même clé autre corps → `422` ; deux envois simultanés → l'un `201`, l'autre `409` ; la
  même clé chez une autre personne est indépendante ; une ligne échue ne compte plus ; la purge efface les
  lignes échues seulement ; une erreur pendant l'effet ne laisse aucune ligne.

### T8 : Les requêtes conditionnelles (`ETag`, `If-Match`, `If-None-Match`)

**Pourquoi :** spec § 3.5 (concurrence), § 3.7 (relecture de la session de cuisine en `304`), § 3.9. Les
colonnes `version` arrivent en 0.5 : ici l'outillage et ses tests.

**Fichiers :** `src/popote_api/conditionnel.py`, tests `tests/unit/test_conditionnel.py` (routeur de test).

- [ ] `etag_de_version(n)` → `"v<n>"` (fort) ; `etag_de_contenu(octets)` → fort, tiré d'un SHA-256 tronqué en
